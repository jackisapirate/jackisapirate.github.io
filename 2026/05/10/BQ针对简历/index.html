第一轮问题（技术深挖版）Return Management System 项目

1. 你们的 Return Management System 为什么要使用 Kafka？和 RabbitMQ 相比，你们是基于哪些考量做的选择??

in our Return Management System, the whole workflow is event-driven. For example, when a customer submits a return, we create a refund event, and multiple downstream services need to consume that same event. So we needed something that can handle high throughput, scale easily, and support multiple consumers.

We chose Kafka mainly for three reasons. First, Kafka gives us very high throughput — we process over a million events a day, and it handles that easily. Second, Kafka’s consumer group model makes it really simple to scale our services independently, and multiple services can consume the same event without duplicating work. Third, Kafka has built-in persistence and replay, so if a downstream service is down or slow, we don’t lose any data and it can catch up later.

RabbitMQ is great for lightweight messaging, but it doesn’t handle large backlogs or horizontal scaling as well as Kafka. So for this project’s volume and event-driven architecture, Kafka was just a better fit.

① Kafka 的 QPS、partition 数量是怎么决定的？为什么？

  • “How many events per second were you processing?”

Sure. In our system we handle a bit over a million refund tansaction which is 20m events per day, which roughly ends up being around 2500 events per second during peak time. It’s not super high, but we still want enough room to grow.

So when we designed our Kafka topics, we picked a partition count based mainly on two things:
how much traffic we expect, and how many consumer instances we want to run in parallel. Since each partition can only be processed by one consumer at a time, the number of partitions basically decides our max parallelism.

We started with a reasonable number of partitions — not too high, not too low — and increased them later when our traffic grew. Kafka makes adding partitions pretty straightforward.

So overall, the partition strategy gave us enough throughput, and it let us scale individual consumers easily whenever one downstream service needed more capacity.

② 你们怎么保证 message 不会丢？怎么保证 exactly-once 或 at-least-once？

常见 follow-up：

  • “What’s your acknowledgment strategy?”
  • “Do you use idempotency keys?”
  • “How do you handle retries?”

In our system, we mainly design for at-least-once delivery, not strict exactly-once.

Because in real-world systems, especially with Kafka, failures can happen between processing and committing offsets, so duplicates are always possible.

To handle that, we make our services idempotent, so even if the same message is processed multiple times, it won’t create duplicate refunds or inconsistent states.

For example, when processing a refund event, we use a unique identifier like eventId, returnId, and we check the database before applying any update. If it has already been processed, we simply ignore it.

On the producer side, Kafka also provides retry mechanisms and acknowledgments, like “acks = all”, to reduce the chance of message loss.

So overall:

  • We ensure no message is lost using Kafka durability + acknowledgments
  • We accept at-least-once delivery
  • And we achieve correctness through idempotent consumer logic

③ 如果 downstream 服务宕机了，你们的系统怎么保证不会崩？

你要讲：

  • Kafka backlog
  • retry strategy
  • consumer group catch-up
  • dead-letter topic（如果有）

If a downstream service goes down, our system doesn’t break because Kafka acts as a buffer.

We don’t call downstream services synchronously. Instead, we publish events to Kafka first, and Kafka will safely store those events.

So if the downstream service is down, it just stops consuming for a while. The messages will stay in Kafka as a backlog.

Once the service comes back up, it can continue consuming from where it left off, so nothing is lost.

In some cases, we also add retry logic or a dead-letter topic for messages that fail multiple times, so we can investigate them later.

So overall, the system is designed to be resilient — Kafka decouples the services, and we rely on eventual consistency instead of blocking the whole workflow.

你们retry多少次? 多长时间后定义为失败?

We don’t have a fixed universal number, but in our system we usually retry around 3 to 5 times with exponential backoff.

So for example, we might retry after 1 second, then 5 seconds, then 10 or 30 seconds depending on the failure.

If the service still keeps failing after all retries, or it keeps failing for a few minutes continuously, we treat it as a downstream outage.

At that point, instead of blocking the pipeline, we send the message to a dead-letter queue and rely on later replay or manual investigation.

So basically, we combine retry + time window + DLQ to decide whether a service is temporarily unstable or really down.

④ 你们怎么防止重复消费？如何保证幂等性？

面试官会说：

“Kafka may deliver a message more than once.
How does your service avoid duplicate refund requests?”

你要讲：

  • idempotency key（基于 returnId 或 transactionId）
  • DB unique index
  • 状态表（processed flag）

In our system, Kafka is at-least-once, so duplicate messages can happen. Because of that, we don’t try to “prevent duplicates completely” at the messaging layer. Instead, we make the consumer side idempotent.

For example, in our refund flow, each event has a unique identifier like returnId . Before processing a message, we first check in the database whether this event has already been processed.

If it has already been handled, we just skip it. If not, we proceed with the refund logic and then mark it as processed in the database.

In some cases, we also use unique constraints at the DB level or an idempotency key table to make sure even if two messages arrive at the same time, only one will succeed.

So overall, the idea is: we accept that duplicates can happen in Kafka, but we make the business logic safe so processing the same message multiple times won’t create any side effects.

⑤ 你们的 refund event schema 是怎么设计的？有没有做 schema evolution？

如果你提到 event-driven，面试官会追问事件结构。

可能的问题：

  • “What fields are included?”
  • “How do you maintain backward compatibility?”
  • “Did you use Avro or JSON?”

The refund event schema is basically the structure of the message we send through Kafka, not a database table. It defines what fields are included in the event, like refundId, returnId, amount, status, and timestamps.

For schema evolution, we follow a backward-compatible approach. That means we can add new optional fields, but we avoid removing or changing existing ones in a breaking way.

For example, if we later added a currency field, older consumers would just ignore it, and newer consumers can start using it without breaking existing services.

In some cases, we also rely on versioning or default values to make sure old and new consumers can coexist safely.

So the main idea is to keep the event schema flexible and backward compatible, so different services can evolve independently.

⑥ 你们有没有用 message ordering？怎么保证顺序？

可能会问：

  • “Do you need strict ordering per returnId?”
  • “How do you handle ordering across partitions?”

你可以回答：
同一个 returnId hash 到同一个 partition。

Yes, we do care about ordering, but only at the business key level, not globally.

In our Return Management system, we need ordering per returnId. For example, all events related to the same return should be processed in sequence.

To guarantee that, we use returnId as the Kafka partition key. Kafka will hash the key and always route messages with the same returnId to the same partition.

Since Kafka guarantees ordering within a single partition, this ensures that all events for the same return are processed in order.

Across different returnIds, we don’t guarantee ordering, because they go to different partitions — but that’s fine for our use case.

So basically, we achieve ordering by controlling the partition key, not by trying to enforce global ordering.

什么是topic

In Kafka, a topic is basically a named stream of messages, like a category where events are published and consumed. Each topic is split into partitions to allow scalability and parallel processing. Messages with the same key go to the same partition to preserve ordering. Consumers then read from partitions in parallel, which allows Kafka to handle high throughput in a distributed way.

⑦ 你们用 Kafka 主要是 async，那某些流程需要 sync response 怎么办？

考你系统设计能力。

In our system most workflows are async because Kafka is event-driven, but yes — sometimes the business needs a synchronous result, like when the frontend expects an immediate status.

In those cases, we simply don’t use Kafka for the request/response part. The client calls our REST API, we do the necessary validation and lightweight processing, and we return a direct response.

If a long-running task is involved, we return right away with something like a requestId, then publish the event to Kafka to continue the async workflow. The client can check the status later or listen for a callback. 这里check the status可以理解为轮询，callback是后端完成后触发notification步骤

So basically, synchronous steps stay within our REST layer, and the heavy, async parts are pushed to Kafka. We don’t force Kafka to act like RPC.

⑧ 你们有没有遇到过 consumer lag？怎么监控？怎么解决？

你要讲：

  • consumer lag metrics
  • 加 partition / 加实例
  • 性能调优（batch size、fetch.max.bytes）

Did you experience consumer lag? How did you monitor and fix it?

Yeah, we’ve definitely seen consumer lag, especially during peak return traffic.
We monitor it using OpenObserve, where we pull Kafka consumer lag metrics — things like the current offset, lag per partition, and the trend over time. If a consumer starts falling behind, we can see it pretty quickly.

When lag happens, we normally fix it in a few ways:

  1. Scale out the consumers — since we’re using a consumer group, adding more instances helps us process partitions in parallel.
  2. Increase partitions if the topic itself becomes a bottleneck.
  3. Tune performance settings, like increasing batch size or tweaking fetch.max.bytes so each poll pulls more data.
  4. Sometimes it’s just slow downstream — so we profile the consumer logic and remove blockers or heavy processing.

So in short: we monitor it through OpenObserve, alert on lag, and fix it by scaling out, adding partitions, or tuning consumer performance.

⑨ 你们的 retry 机制怎么设计？有没有 dead-letter topic？

很多公司一定会问。

How we designed our retry mechanism

In our system, yes — we have a retry mechanism, and we also use a dead-letter topic.

So basically, when our consumer fails to process a message, we don’t retry immediately in a tight loop 字面意思是紧密循环：不间断、很频繁、没有等待时间的重复执行循环. Instead, we send the failed message to a retry topic with some delay. We usually have multiple retry levels, like retry-5-seconds, retry-1-minute, etc. This gives the downstream system some time to recover.

Each retry topic has its own consumer group, and after the delay, the message gets consumed again. If it still fails after all retry attempts, we finally push it into a dead-letter topic. That’s where we store permanently failed messages for manual investigation.

We also add metadata — like the error reason, retry count, timestamp — so it’s easy for us to debug later.

Do we have a dead-letter topic?

Yes, we do. Our dead-letter topic is mainly for:

  • messages that are poisoned (always fail)
  • unexpected data format
  • downstream service issues that don’t recover
  • anything exceeding the max retry count

We monitor the DLQ, and if we see unusual spikes, we investigate immediately.

⑩ 如果 Kafka 整体宕机，你们系统怎么处理？有没有 fallback？

视你公司实践而定。

If Kafka goes down, how does our system handle it? Do we have a fallback?

Yeah, we actually thought about the “Kafka is down” scenario, because it does happen in real life — like broker outages, Zookeeper issues (Kafka 3.5+ 基本默认就是 no-Zookeeper architecture), or a bad deployment.

Here’s how our system handles it:

1. First of all, our producers don’t crash — they buffer

When Kafka is unavailable, our producer retries automatically.
We tune parameters like:

  • retries
  • retry.backoff.ms
  • max.block.ms
  • delivery.timeout.ms

So instead of failing immediately, the producer will keep retrying for some time. This prevents a request from failing just because Kafka is temporarily unstable.

If Kafka is still down after the timeout, we log the failure and return a controlled error to the caller.

2. We write the failed messages into a fallback storage

Yes — we use a fallback mechanism.

Basically, when Kafka is fully unavailable and we’ve retried long enough, we don’t want to lose the data.
So we write the payload into something like:

  • a local file (short-term buffer), or
  • a backup database table, or
  • a temporary Redis queue

This gives us a place to “park” the messages until Kafka comes back.

Later, we have a small job that replays these messages back into Kafka.

This way, we don’t lose data even during a Kafka outage.

3. On the consumer side, we actually become “idle” instead of erroring

If Kafka is down:

  • our consumers simply cannot poll new messages
  • they just sit idle
  • no business logic is broken
  • everything resumes automatically when Kafka is back

We don’t need a special fallback on the consumer side — Kafka handles the offsets, so once brokers recover, consumption continues from where it stopped.

4. We have alerts if Kafka is down

We monitor:

  • consumer lag
  • broker health
  • partition offline count
  • under-replicated partitions
  • producer send failure rate

If Kafka dies, alerts fire immediately so the platform team can restore the cluster.

5. The key idea

We don’t try to “replace Kafka” when it’s down — that’s too complex.
What we do is:

  • protect producers from losing data
  • let consumers recover gracefully
  • store failed messages temporarily
  • replay after Kafka is back

This is realistic and common in financial systems.

2. 你们的 Kafka topic 是如何设计的？partition 数量、replication factor 是怎么设置的？QPS 大概多少？有没有遇到 backpressure？

Sure — in our project we used Kafka pretty heavily, mainly for event streaming between services and for buffering high-throughput write workloads.

Topic Design
We designed topics around clear business domains — for example, returns.created, inventory.updated, and order.status.changed.
Each topic only carried one event type so the consumers stayed simple.

Partitions & Throughput
For our hot topics, like returns.created, we configured 12 partitions.
We started with 6 but doubled it when the traffic grew because we needed more parallelism on the consumer side.
Our typical throughput was around 8k–12k messages per second depending on peak hours.

Replication Factor
We used replication factor = 3, which is pretty standard.
It gives you good durability and allows Kafka to tolerate a broker failure without losing availability.

Backpressure & Consumer Lag
Yes, we did run into backpressure in a few scenarios — usually when downstream services slowed down or the database had spikes.
We handled it in a few ways:

  1. Horizontal scaling — we added more consumer instances so each partition had a dedicated consumer.
  2. Batch consumption — instead of processing one message at a time, consumers processed in small batches to reduce DB I/O.
  3. Dead letter queue — slow or malformed events were diverted instead of blocking the main consumer loop.
  4. Autoscaling — we scaled consumers based on lag metrics so we reacted automatically when traffic spiked.

Overall, our system was stable even under heavy load because Kafka gave us enough buffering capacity and the consumer side was able to scale horizontally.

3. 在 Return workflow 中，event-driven workflow 是怎么设计的？比如一个 refund event 从产生到消费完整流程能讲一下吗？

Sure — in our return workflow everything is event-driven, so a refund basically flows through a series of events.
When a customer submits a return request, our service first validates it and writes the return record into Azure SQL. Right after that, we publish a ReturnCreated event to Kafka. That’s like the trigger for the whole refund pipeline.

Our Refund Orchestrator service consumes that event and decides what should happen next — for example, check inventory rules, verify payment method, or calculate the exact refund amount. After each step, it publishes another event, like RefundCalculated or RefundApproved, so downstream services don’t call each other directly — they just react to events.

Once the refund is approved, we publish a RefundRequested event. Our Payment Service listens to that topic. It handles the actual payment refund with the payment provider, and when the provider confirms success, it emits a RefundCompleted event.

Finally, another consumer updates the return status in SQL, logs everything for auditing, and triggers user notifications.

So the idea is:
each step is small, decoupled, and asynchronous.
Events drive the workflow, and every service only needs to care about the events it consumes and produces.

4. 你简历中提到了 Azure SQL Database，每天 100 万+ transactions。你们怎么保证高吞吐？是否做了 connection pool 优化、batch write、index 调优？

Sure — in my previous project we were handling over a million transactions per day on Azure SQL Database, so keeping the throughput high was a big focus for us.

First, on the application side, we made sure to use a proper connection pool. We tuned the pool size based on our peak load tests, so the app didn’t spend time repeatedly opening and closing connections — which is pretty expensive for SQL Server.

Second, we optimized the way we wrote data. Instead of sending a lot of small INSERT operations, we switched to batch writes and used table-valued parameters for bulk insert scenarios. That significantly reduced round-trips and improved throughput.

Table-Valued Parameters（TVP，表值参数）是 SQL Server（包括 Azure SQL Database）里的一个特性：允许你把“一整张表”当作一个参数传给 SQL / 存储过程

On the database side, we spent a lot of time on index tuning. We added covering indexes for our hot paths and removed a few unused ones to reduce write overhead. We also monitored DTU/CPU usage and Query Store to catch expensive queries early.
hot path = 最频繁被访问的 SQL 路径， 删除不常用的针对某列的整个儿索引，DTU = Database Transaction Unit

Finally, we implemented retry logic with exponential backoff because Azure SQL can occasionally throttle “节流阀” or cause transient failures, and we didn’t want those to slow us down.

Overall, by combining connection-pool tuning, batching, and index optimization, we were able to keep the system stable even during peak traffic.

为什么说 “improves hot paths”？

因为：

  • 高频查询 → 减少 IO
  • 避免回表 → 降低 latency
  • 提高 QPS

On the other hand, we used Azure SQL Database for the core return workflow, such as return requests, return status, and transaction records, where we needed strong consistency and relational integrity.

So basically, we separated the responsibilities:
SQL for transactional and consistent data, and MongoDB for flexible product attribute data.

追问 SQL + NoSQL 的划分 & 你负责的内容

Sure — in our project we actually used both a relational database, Azure SQL, and a non-relational database, MongoDB.

Azure SQL was mainly used for all the structured and transactional parts of the system — things like return orders, workflow states, audits, payment status, basically anything that required strong consistency and relational constraints.

But for the product-related data, we used MongoDB.
The reason is that different product types had very different sets of fields. Some had size and color, others had serial numbers, others had expiration dates… the schema wasn’t stable. So putting that into a relational table would have led to dozens of nullable columns or complicated join tables. MongoDB handled that flexible schema much better.

In this design, my role was:

  • modeling the JSON documents in MongoDB
  • building the queries for retrieving product attributes
  • designing how our return service combines SQL data (the return itself) with NoSQL data (the product attributes)
  • and making sure we only put transactional or relational logic into Azure SQL, while the dynamic product metadata stayed in MongoDB.

So the separation was pretty clean:
SQL = structured, transactional, consistent.
NoSQL = flexible, schema-light product attributes.

Abstract Class: 1) still a class, so you can only extend one abstract class. 2) Have both concrete method and abstract method.

Interface: 1) you can implement many interfaces 2) Only has abstract method. 3) In java 8, interface can have default and static method

Usage:

Most of the places, interfaces are preferred, but if you need some common method to inherit automatically, you can use abstract class.

HashMap: how does it work internally, what is hash collision

HashMap has 2 important methods, equals() and hashcode()

Think there is a list of buckets, each bucket is identified by a hashcode.

When you call get(key), the key will first be passed to hashcode() method and a hashcode is returned, Use this hashcode, you can locate the corresponding bucket. Inside that bucket, it is a tree structure of all key-value pairs that share the same hashcode. so to find the target key-value pair, the equals() method will be called, and once found, the value will be returned.

Hash collision: all the key-value pair that shares the same hashcode stays in same bucket, that is called hash collision. It is preferred in hashmap, because if there is NO hash collsion, each key-value pair will stay in one bucket, then there will be too many buckets, causing too much memory. If all entries in one bucket, then it is hard to search the target. The hash collision makes the time complexity of hashmap to O(1) because of hashing.

Why hashmap use Tree structure in bucket: Previously it is a list, but then changed to tree, because tree has left node smaller than root and root smaller than right. So the search is O(logn), much faster than list.

为什么equals 和 hashcode的返回值必须一致

In Java, the contract between equals and hashCode requires that if two objects are equal according to equals(), they must have the same hashCode.
This is because hash-based collections like HashMap and HashSet first use hashCode to locate the bucket and then use equals to find the exact match.
If this rule is violated, logically equal objects may be stored in different buckets, leading to incorrect retrieval behavior.

Optimistic locking and pessimistic locking mainly differ in how they handle conflicts. 注意：这两个单词发音

Optimistic locking assumes conflicts are rare.
So it doesn’t actually lock the data when you read it.
Instead, when you try to update, it checks whether the record has changed — usually with a version field.
If someone else updated it, your update fails and you retry.
This works really well in read-heavy and low-contention situations.

Pessimistic locking assumes conflicts will happen.
So it locks the record as soon as you read it — for example using SELECT … FOR UPDATE.
Other transactions have to wait until the lock is released.
It’s safer, but it can reduce concurrency, and it’s usually used in high-contention or financial systems.

In short:
Optimistic locking = no lock, check version, retry if needed.
Pessimistic locking = lock first, block others.

What is the CAP theorem?

The CAP theorem says that in a distributed system, you can’t have Consistency, Availability, and Partition Tolerance all at the same time.You can only guarantee two of them.

Consistency means every node sees the same data.
Availability means the system always responds.
Partition Tolerance means the system keeps working even if the network between nodes fails.

In real distributed systems, network partitions are unavoidable, so you must choose between CP and AP.

  • CP systems prioritize consistency over availability.
  • AP systems prioritize availability and allow eventual consistency.

So, the main idea is: you can’t have all three — you must trade off depending on your system’s needs.
